# Bug Report: Incomplete Command History Capture

**Target Version for Fix:** v5.1.0
**Status:** Open

## Description
The user reported that only partial input/output data is being captured and persisted to the session databases. Specifically, only a subset of output is making it into the command history.

## Observed Behavior
- "Only some output and is captured in the commands-history."
- This indicates a loss of data integrity or a semantic parsing failure during the recording pipeline from the PTY (`ads-shell`) to the SQLite database.

## Potential Causes to Investigate
1. **OSC 133 Scanner State Loss**: The `command_history` table is populated by the `ansi.OSCScanner` state machine, which relies on specific OSC 133 escape sequences (A, B, C, D) injected by shell hooks. If these markers are mangled, split across 4096-byte chunk boundaries improperly, or bypassed by certain interactive applications, the scanner may drop the command output.
2. **Raw Stream vs Semantic Parse**: We need to determine if the raw data itself is missing from the underlying `io_stream` table. 
   - *If `io_stream` has the data but `command_history` doesn't:* The bug is in the `ansi.OSCScanner` logic.
   - *If `io_stream` is also missing the data:* The bug is upstream in the `ads-shell` `io.Copy`/`Read` loop or PTY buffer dropping.
3. **Premature EOF/Flush Failure**: When a session closes or a command exits rapidly, the final chunks of the PTY buffer might not be flushed to the database before the background goroutines are terminated.

## Initial Findings from Live Database Inspection
Following access to the user's live database directory (`/home/dada/.local/share/ads/sessions/`), I inspected recent sessions (e.g., `2d7e8208-d204-4916-9df3-81ee206d5625.db` and `ef254479-d423-4904-9fd8-0b0fff5da893.db`).

**Key observations:**
1. The `command_history` table schema only contains `id`, `command_text`, `start_ts`, `end_ts`, and `exit_code`. It does not explicitly store the command output natively within the table.
2. The `io_stream` and `fts_index` tables are successfully capturing thousands of chunks per session, which contain the output data. 
3. If the user is observing missing output when using `ads search`, it's likely that the OSC 133 semantic segmentation logic inside `ansi.OSCScanner` is not accurately associating output chunks with their corresponding commands, or perhaps the ANSI stripping logic is filtering out valid payload text from the FTS indexing pipeline.

**Next Steps:**
1. Determine if we need to explicitly link `io_stream` outputs to specific `command_history` IDs via foreign keys, or modify `OSCScanner` to store the raw output directly alongside `command_text`.
2. Trace the FTS search integration to see exactly how output is missing from user searches.
3. Fix the `OSCScanner` in the `fix/v5.1-history-capture` branch.
