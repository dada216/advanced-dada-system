# ADS v3.0.0 Plugin Architecture & LLM Backend

## 1. Executive Summary
The v3.0.0 release represents a monumental shift for the Advanced Dada System (ADS). It transitions the monolithic CLI into a modular ecosystem powered by `hashicorp/go-plugin`. By decentralizing heavy analytical workloads (like Federated Search and LLM Analysis) into isolated plugin binaries communicating over gRPC, ADS guarantees absolute stability for the core recording loop while enabling infinite extensibility.

## 2. Core Objectives
1. **Plugin System Transition**: Integrate `hashicorp/go-plugin` to support multi-process, gRPC-based plugins over Unix domain sockets.
2. **Search as a Service**: Extract the existing `internal/search` FTS5 federated query engine into a standalone plugin binary (`ads-plugin-search`).
3. **LLM Backend**: Implement an OpenRouter-powered LLM service plugin (`ads-plugin-llm`).
4. **Testing Rigor**: Substantially increase Unit, End-to-End (E2E), and Interactive test coverage across the ecosystem.

## 3. Plugin Architecture (hashicorp/go-plugin)

### 3.1 Interface Definition
A universal Go interface will be defined in a new `internal/plugin` package to establish the RPC contract:

```go
package plugin

import "net/rpc"

// Service is the interface that plugins will implement.
type Service interface {
    RunTask(args map[string]string) (string, error)
}
```

### 3.2 Binary Distribution
Plugins will be compiled as independent binaries and dropped into a known directory (e.g., `~/.local/share/ads/plugins/`).
- `bin/ads` (Core Orchestrator)
- `bin/ads-recorder` (Core Recorder)
- `bin/ads-plugin-search` (Search Plugin)
- `bin/ads-plugin-llm` (LLM Plugin)

The core `ads` binary will act as the Plugin Host, spawning these binaries dynamically when their respective CLI commands are invoked.

## 4. Search Plugin (`ads-plugin-search`)
The current `ads search` command will be refactored to act as a proxy. When `ads search "query"` is executed:
1. The Orchestrator spins up the `ads-plugin-search` binary via `go-plugin`.
2. It passes the search term via gRPC.
3. The plugin independently queries the `meta.db` and federates out to the `sessions/*.db` files.
4. The plugin returns the aggregated, formatted results back over gRPC to the Orchestrator for standard output.

## 5. LLM Backend Plugin (`ads-plugin-llm`)
The `ads-plugin-llm` will introduce native AI analytics to terminal sessions.

### 5.1 OpenRouter Integration
The plugin will communicate with OpenRouter's API.
- **Authentication**: The API key will be managed securely via a secret file (e.g., `~/.local/share/ads/secrets/openrouter.key`) or an environment variable `ADS_OPENROUTER_KEY`.
- **Functionality**: 
  - `ads llm summarize <session-name>`: Fetches the raw text from a session's `fts_index` (or semantic chunks), packages it into an LLM prompt, and streams the summary back.
  - `ads llm ask <session-name> "Why did my build fail?"`: Uses the session context to answer specific user queries.

## 6. Testing Strategy
To support this modular architecture, the `Makefile` testing pipeline must be hardened:
- **Unit Tests**: Focus on the RPC boundaries and parameter marshaling in the `internal/plugin` package.
- **E2E Tests**: Mock the OpenRouter API endpoint. Validate the full lifecycle: Session Creation -> Recording -> Plugin Invocation -> Result parsing.
- **Interactive Tests**: Expand `integration.sh` to leverage `tmux send-keys` to simulate live user sessions being dynamically parsed by the new plugins.

## 7. Migration Plan
1. **Phase 1**: Scaffold `hashicorp/go-plugin` interfaces and test the Host/Client handshake.
2. **Phase 2**: Extract `search` into the plugin architecture. Verify zero performance degradation.
3. **Phase 3**: Implement `ads-plugin-llm` with OpenRouter integration and Secret management.
4. **Phase 4**: Write comprehensive Unit and E2E tests for the new plugin boundaries.
